# 横小艺韵：学校官网接入与十机访问排查

供学校信息老师或网站服务商评估。日期：2026-10-23。项目为现有React页面 + Node.js后台 + SQLite + 本地图片/视频，包含登录、内容上传、留言和Excel。以下是环境需求和代码审计结果，不代表已经部署学校服务器或通过校园网络验收。

## 一、这次现场现象能确定什么

用户反馈：Mac提供局域网展馆，约十台手机在其他办公室同时扫码，部分图片和视频加载不出；此前Windows也曾在重启服务后恢复。

已核对1.4.3代码：凤冠当前会以每个页面4个加载任务预取整组91帧。仓库这组WebP为1600×1600，合计 **33,640,600字节，约32.08 MiB**；十台无缓存手机完整加载这一组，累计约 **320.82 MiB**，还不含视频、其他图片和页面资源。浏览器缓存命中时不会每次产生相同传输量。十台客户端的帧预取在加载阶段可能合计约40个任务，尚不含视频。

这是明确的加载压力点，不能据此直接判定现场唯一故障原因。还需要区别无线覆盖/AP拥堵、电脑无线链路、不同办公室的VLAN或访客隔离、电脑休眠/地址变化、影片码率/兼容性、请求失败或进程异常。当前视频默认使用metadata预加载，并非进首页就下载全部三部影片。灰色播放器和“重启后恢复”均不足以单独确定原因。

学校局域网地址下的素材流量主要走校园内网，不一定经过互联网出口；“学校上网带宽不大”与“办公室到这台Mac的实际速度”是两个指标。Mac和手机都走无线时，服务器端的Wi-Fi也会占用无线资源，优先评估电脑有线接入。

## 二、推荐的官网接入方式

建议由学校官网增加“横小艺韵”入口链接，展馆使用学校管理的独立HTTPS子域名，例如 `https://yiyun.school.example/`（仅为占位示例，不是真实学校地址）。

访问链路：手机 → 学校HTTPS入口 → Nginx/Caddy反向代理 → Node应用 → 私有持久化数据目录。

这需要能长期运行Node服务的服务器或容器；普通CMS上传页面/FTP静态空间不足以承载后台、留言、上传和Excel。当前路径以 `/assets/`、`/api/`、`/admin` 等根路径组织，独立子域名改动最少；若必须放在官网 `/yiyun/` 子目录，需要先适配程序路径。当前安全策略禁止iframe嵌入，不能承诺直接把网页嵌进官网页面即可工作。

## 三、请学校提供/确认的环境

| 项目 | 当前需求或建议 |
| --- | --- |
| 运行位置 | 学校或现有服务商维护的长期在线服务器/虚拟机/容器；建议Linux，避免依赖教师电脑和终端窗口 |
| 运行环境 | **Node.js >=24.15.0 且 <25**，例如24.22.0；已有构建文件时正常运行无需npm安装开发依赖 |
| 初始资源 | 建议为小规模试运行预留约2核CPU、4GB内存、40GB可用SSD，再按素材、备份及实测调整；这是规划起点，不是已经证实的并发容量 |
| 数据库 | Node内置SQLite，单应用实例；无需另开MySQL/PostgreSQL端口，不直接多实例共享SQLite文件 |
| 持久化 | data目录可写，含数据库、配置、上传素材；容器须挂载持久卷。备份任务也需有可写目标，不因重启/更新而清空 |
| 网址/证书 | 学校提供子域名、DNS及匹配的HTTPS证书，按学校现有域名管理流程处理 |
| 服务托管 | systemd或学校现有进程托管，开机自启、异常重启、访问/错误日志、磁盘与进程监控 |
| 网络范围 | 明确仅校内访问，还是家长在校外用手机流量也能访问；后者需要真实公网入口 |
| 网络承载 | 服务器优先千兆有线接入；核对办公室AP、回程链路和各网段到服务的实际速率，不只看互联网套餐标称带宽 |
| 素材服务 | MP4支持GET/HEAD、HTTP Range/206分段读取，保留Content-Range/Content-Length等头；图片视频请求不能被官网路由改成HTML |
| 后台上传 | 程序整片上限400MiB、按8MiB分片；反向代理单请求上限建议至少16MiB，上传/读取空闲超时按慢网实测配置 |
| 内容与接口 | 正式站点origin设置为实际HTTPS网址；代理保留必要请求头，登录和留言保持同源；不缓存会话、后台或私密接口 |
| 日常维护 | 明确学校或服务商的维护人、完整备份计划及恢复检查；备份含数据库、配置和上传媒体，不能用Excel替代 |

前端源码维护/重新构建时才需要开发依赖。现有部署示例在 `deploy/Caddyfile.example`、`deploy/fenghua.service`、`deploy/install-service.sh`，应由信息老师按实际环境调整，不将示例当作已完成配置。

首次以服务方式启动前，应在部署准备阶段还原第二/三视频的仓库分片并确认素材完整，再按学校权限策略运行。备份目标权限也需单独配置；目前systemd示例只给data写权限，不能据此假设所有备份位置都可写。

## 四、需要哪些端口

| 端口 | 用途与开放范围 |
| --- | --- |
| **TCP 443** | 观众访问正式HTTPS站点；由学校网站网关/反向代理对目标访问范围开放 |
| TCP 80 | 按学校现有HTTP跳转或证书验证方案选择；使用其他证书方案时不一定需要 |
| **TCP 3000** | Node应用默认内部监听端口，通常仅 `127.0.0.1:3000` 供同机代理访问；**无需直接对公网开放**。代理与应用分机时，仅放行指定代理到应用的私网连接 |
| 运维端口 | SSH/堡垒机等由学校按自身管理方式提供，限维护人员；不属于学生扫码访问需求 |

不要求给所有手机开放数据库端口。正式服务不使用教师电脑的 `172.22.*.*:3000` 作为长期公网网址；二维码应改为学校正式HTTPS地址。

若暂时继续使用Mac/Windows局域网启动：需确认手机所在办公室网段允许连接该电脑**当前实际IP的TCP 3000**（或启动窗口显示的实际端口），并检查AP客户端隔离、访客网络策略与电脑入站权限。“同一个Wi-Fi名称”不保证不同办公室可以互访；不建议关闭整个防火墙。

## 五、带宽如何估算

视频主要按实际码率和同时播放人数估算。举例：每部提供约2Mbps的观看副本，十台同时播放约需20Mbps有效传输，再为协议、图片和波动留余量，可按30–50Mbps以上有效链路进行试运行规划。这里的2Mbps是规划示例，**没有测量用户Mac上实际上传影片的码率**。仅给文件大小而没有时长，无法判断播放所需带宽。

校内服务应测“服务器到各办公室手机”的路径；公网部署还要核对服务器出网和观众网络。千兆网卡、100M标称端口或更大互联网带宽都不能直接代替端到端实测。

当前约321 MiB十机首轮凤冠数据还会带来额外突发流量。因此上线前应同时安排按需/分阶段加载凤冠、限制后台预取、失败可重试、合理缓存，以及保留原片的低码率兼容视频副本。进一步CDN/静态素材分发或自适应视频可按实际需求评估，当前未配置，也不是学校必须先购买的服务。

## 六、现场先做的三个检查

1. 电脑有线接入、接电、不休眠，保持展馆运行；核对启动窗口的实际IP/端口。请信息老师从出问题的办公室用同一地址检查 `/api/health`（正常为 `{"ok":true}`）和一张图片。若同办公室连健康接口也失败，优先查网络路径/隔离/主机状态；若健康接口正常、素材慢，再检查媒体请求、码率和加载队列。
2. 按1台、5台、10台逐步同时打开，记录所在办公室、图片出图时间、视频开始播放/缓冲和留言提交情况。测试要覆盖首次无缓存访问，避免把浏览器缓存后的速度当成首次加载能力。
3. **重启前**保留错误提示、终端日志及时间，请信息老师对照HTTP状态、服务器进程/资源和网络日志。404、502/504、请求超时、文件读取错误与浏览器正常取消请求需要分别判断；不能将所有错误都当成同一问题。

管理员密码不写入交接文档。正式域名和真实data迁移，应先核对当前目录、备份，再单独安排；不直接覆盖教师电脑上的旧数据。观众查看完整站点不依赖GitHub或ChatGPT，但是否能在校外直连仍取决于学校实际公网配置与验证。
